# Testing OpenPlainEnglish

Use invented text and public-information examples. Do not test with medical records, private account pages, browser profiles, credentials, or real feedback exports.

This is the v0.4 test plan, not a completed native-browser checklist. Native installation, upgrade, file-picker import and store acceptance remain unverified. The [v0.4 verification record](RELEASE-0.4.0.md) lists completed checks and remaining gaps; the [v0.3 record](RELEASE-0.3.0.md) is historical evidence for that version only. Actual participant sessions completed: **0**. Keep release results separate from the checks below.

## Automated checks

The development toolchain supports Node.js 22 and 24. Starting from the repository root:

```sh
npm ci
npm run check
npm run package
npm run package:firefox
npm run package:sdk
npm run check:coverage
```

`npm run check` validates both lexicons, runs Node's test runner, and builds the Chromium extension. The package commands create the Chromium ZIP, unsigned Firefox preview ZIP, and standalone SDK tarball, each with a SHA-256 sidecar. A successful build alone does not verify browser behavior or the accuracy of an explanation.

The current automated tests cover:

- **Matching:** case-insensitive terms and aliases, longest phrases, repeated terms, punctuation, Unicode boundaries, and adjacent text that must not match.
- **Page handling and modes:** Plain reading / Explain terms transitions, enable/disable cycles, one-occurrence restoration, ignoring a term for the current page, preservation of website edits, dynamic content, skipped editable/interactive/hidden content, and bounded work on large pages. Split phrases across supported inline formatting retain their elements and count as one logical match. Print-event and original-text extraction tests are DOM simulations, not native print or clipboard verification.
- **Replacement eligibility:** explicit source-checked pairs, supported word forms and capitalization, separate replacement/explanation counts, and annotation-only fallback. The 112-entry health glossary contains 21 entries with 40 replacement pairs; a glossary match does not imply an approved replacement. The separate opt-in public-service pilot has 8 entries and 14 pairs. It is available to the workshop and SDK, not bundled into the extension's health dictionary. See the [pair ledger and exclusions](INLINE-LEXICON.md).
- **Preferences and commands:** validation and safe defaults for English/Chinese interface language, density, highlighting and remembered mode; serialized local storage updates; off-state selection without activation; keyboard command dispatch. Mock command events do not establish that a native browser assigned or granted a shortcut.
- **Feedback and background actions:** allowed fields, sanitization, the newest-100-record limit, concurrent saves, UI draft creation and review, confirmed deletion, supported-page checks, authoritative glossary metadata, reviewed report copy/download and encoded issue URLs. No page URL, title or body is automatically added. Clipboard-denied fallback uses selectable text.
- **Lexicon:** schema, unique entries, sources, licensing, review metadata, and supported term/alias relationships.
- **Backup import:** strict schema/UTF-8 size/record bounds, atomic rejection, preview before confirmation, deduplication, overflow reporting, historical metadata preservation and serialization with saves/deletes.
- **Bundled integration:** real bundled popup, background and content scripts communicate in isolated in-memory contexts, including off-state mode selection without activation, active mode changes, restoration, feedback and recovery after malformed messages. The browser APIs are test doubles; this does not emulate Chrome's permission grant or native extension host.
- **Workshop and study:** pasted-text restoration, latest-domain-load handling, no paragraph persistence, copy fallback, cross-format phrase extraction, balanced study sequences, explanation-open counts and export allowlists. Synthetic harness runs are not participant sessions.
- **Distribution, SDK and website:** archive inspection, payload/asset allowlists, checksums, deterministic ZIP packaging, version/permission/CSP guards, SDK text-engine boundaries and repository-prefix static-site assets.
- **Source checker:** offline fixtures for HTTP failure classes, timeouts, concurrency/retry limits, dynamic term evidence and title extraction. Live source availability is checked separately.

The build checks that package, manifest and lexicon versions match, bundles the scripts, and copies declared assets. Packaging rebuilds the extension and writes a ZIP and SHA-256 checksum. Tests inspect archive contents and bytes against the build; CI additionally runs `unzip -t` and verifies the checksum with system tools. Actual browser installation still requires the checklist below.

CI repeats the commands above on Node.js 22 and 24. Each job inspects ZIP integrity, verifies package checksums and uploads the archives for inspection. The online demo deploys only after both jobs pass on `main`. A CI artifact is a test build; a versioned GitHub Release is the user-facing release. The SDK tarball is not an npm registry publication, and the Firefox ZIP is not an AMO-signed installer.

For a production-shaped static preview, run `npm run preview:site`; it serves the built site beneath `/openplainenglish/` to exercise GitHub Pages paths. A source run with `npm run dev` serves `/demo/`. Run `npm run check:sources -- --output artifacts/source-audit.json` for a separate, non-mutating live-source report; inspect failure counts even if the process exits successfully.

`npm run check:coverage` measures known editorial fixtures, not population coverage. `npm run check:compatibility` checks downloaded public HTML in a DOM simulation; it does not execute the sites' scripts or reproduce their layout, browser permissions or assistive technology. Record fixture dates, failures and limits separately from installed-extension results.

## Browser checks before release

Load the built `dist/` folder through **Load unpacked** on the browser's extensions page. Run `npm run dev` and open the demo URL it prints. Inspect the extension's popup, content-script context, and management page as needed; ordinary website requests are separate from extension-origin requests.

Leave the demo page's own reader disabled while testing the installed extension. `/demo/preview.html?view=options` and `?view=popup` use mock browser APIs to preview layout; draft storage there is separate from extension storage. A successful preview does not count as a successful extension runtime check.

Record the browser and version, extension version/commit, page or fixture used, results, and any limitations. Check Chrome and Edge when available; clearly record a browser that was not tested.

1. **Install and activation.** Confirm the unpacked extension loads without errors. Before activation, an HTTP(S) page has no injected marks or changed text. Select **Explain terms** while off and confirm it does not activate the reader; select **Plain reading**, then **Read in plain English**. In the invented fixture `Hypertension and biopsy are health terms.`, expect `High blood pressure and biopsy are health terms.`, one replacement and one unchanged term with an explanation. The popup must distinguish these counts.
2. **Modes and restoration.** While active, choose **Explain terms** and verify all original wording is shown with annotations. Return to **Plain reading** and verify eligible phrases change again without duplicate marks. Restore one occurrence through its panel and check that other occurrences still use their selected presentation. Ignore a term for this page and confirm all its marks disappear, including later added occurrences. Choose **Restore original** and compare untouched text exactly, including capitalization, punctuation and whitespace. Reopening the popup must show the active state and remembered mode. Reloading or navigating to a new document must start disabled and clear page-session ignores.
3. **Explanations and coverage.** Open a replacement and inspect its original wording, short meaning, fuller explanation, context, sources, and honest review status. Open an annotation-only term such as `biopsy`; its definition must not be inserted into the sentence. Check multiword phrases, aliases, repeated terms, punctuation boundaries, unusual mixed capitalization, already plain aliases and unrelated words. An annotation-only page must report zero replacements without implying failure. Search the glossary for `high blood pressure` and inspect the explicit from/to pair and boundary note. Source navigation must happen only after selecting a link.
4. **Preferences and upgrade defaults.** In **Reading preferences**, save Chinese, Compact, Strong and Explain terms; reopen the popup and options page and confirm persistence. Check Chinese controls, dynamic counts, errors and feedback dialogs; English glossary text and authored notes must remain unchanged. Check an active panel and marks update. Changing preferences while off must not activate or inject a reader. An older installation without `opePreferences` must receive English, Comfortable, Subtle and Plain reading defaults without altering its drafts; test invalid saved fields with an isolated synthetic profile. Follow the [upgrade procedure](UPGRADING.md) with a backup before testing real version transitions.
5. **Keyboard, shortcuts and layout.** Reach mode radios, primary action and marked phrases by keyboard; open a phrase, close it with Escape and confirm useful focus returns. Check one focus stop for a phrase split across inline formatting. Inspect narrow width, 200% zoom, both densities and highlights, focus visibility, error announcements and Chinese text wrapping. Test Ctrl+Shift+L to toggle and Ctrl+Shift+U to restore; on macOS use Control, not Command. Inspect assignment at `chrome://extensions/shortcuts` or `edge://extensions/shortcuts` when conflicts occur. Restore must not activate an off reader. Record native screen-reader results separately; DOM accessibility attributes alone are insufficient.
6. **Page safety, formatting and mutations.** Confirm forms, editable areas, links, buttons, code, hidden text and extension-owned UI are skipped. In `/demo/compatibility.html`, exercise dynamic additions, host edits, split phrases and large-page limits. For `blood <strong>glucose</strong> and magnetic <em>resonance</em> imaging.`, expect one replacement and one annotation across two logical phrases; restore the text and retain the existing elements. A phrase crossing a link, button or block boundary must not be joined. Edit text inside a mark, replace a subtree, and hide or make a region editable. Restoration must preserve the site's new text. Repeat mode/restore cycles without duplicate marks, loops, stale panels or growing counts after removal.
7. **Copy, Find and print.** Confirm ordinary browser copy and Find operate on the currently displayed wording. The extension does not override clipboard events. Inspect native print preview in Plain reading: original words should be used and explanation UI omitted; cancel printing and verify the reading view returns. DOM `beforeprint`/`afterprint` tests are only preparation for this check.
8. **Privacy and feedback.** Save invented known-term feedback and a new-term suggestion. Review each, use **Copy report** and **Download report**, and compare the text with the preview. Confirm clipboard denial leaves selectable text and cancellation keeps the draft. These actions need no GitHub account and send nothing to the project. Separately test **Export JSON**, import preview/cancel/merge, and confirmed deletion. Inspect the seven stored fields: no page context is added. The text report is not an importable backup. **Open GitHub draft** must be explicit and must not publish automatically; check its text without posting a test issue.
9. **Network and permissions.** Verify exactly `activeTab`, `scripting` and `storage`, without host permissions. Ordinary matching, substitutions, explanations, preference changes and local draft operations must not make extension-origin external requests. Source and GitHub navigation are expected only after the user's action. Do not mistake an extension-local glossary load or ordinary page requests for an external reader request.
10. **Unsupported surfaces.** Browser-internal pages, PDF files and PDF viewers must not claim support. Iframes and shadow roots are skipped. Only bounded transparent inline formatting is joined; complex formatting can remain unmatched. A no-match page must show an honest zero-result state. The workshop accepts already extracted text but performs no PDF parsing, OCR or file reading.
11. **Release archive.** Extract the produced ZIP into a fresh folder and load that folder, not the source `dist/`. Review archive contents for source maps, caches, credentials, feedback files or other unintended data. Check native Chrome and Edge separately; an available package or store link is not installation evidence.

## Workshop, study and additional packages

- **Workshop:** open `/demo/workbench.html`. Paste invented English text, apply the health glossary, compare originals and copy each view. Edit the input and confirm stale reading output is cleared. Switch explicitly to the 8-entry public-service pilot, including rapid domain changes; only the latest selection may apply. Check one-occurrence restore, ignored terms, full restoration, clipboard fallback and Clear text. Reload and confirm the paragraph is not restored from storage. Test on actual mobile browsers separately from desktop viewport emulation.
- **Study harness:** open `/demo/study.html` and follow [USER-TESTING.md](USER-TESTING.md). Rehearse practice, each balanced sequence, Original / Explain terms / Plain reading, explanation counts, original consultation, skips, interruptions, Stop and reviewed JSON download with synthetic responses. No response should persist after reload or upload automatically. These are software checks; actual participants remain **0** until consented sessions are conducted and documented.
- **Firefox preview:** inspect `release/openplainenglish-0.4.0-firefox-preview.zip`, its checksum and Firefox-specific manifest, then perform native developer loading and the applicable checklist in Firefox 140 or later. Check the background lifecycle, permissions, shortcuts, storage and clipboard behavior. The ZIP is unsigned; AMO signing, submission and native acceptance remain pending. It is not a normal one-click installer.
- **SDK:** inspect `release/openplainenglish-core-0.4.0.tgz` and its checksum; install the tarball in an isolated sample project and execute the [SDK examples](SDK.md). Check original offsets, exact original text, annotation mode, truncation and ordinary handling of HTML-looking text. Opt into the pilot explicitly. There is no npm registry publication or automatic network/model call. A consuming application needs its own rendering and browser tests.

## Preparing a versioned release

For native upgrade/import verification, preserve invented drafts in an older installation, export a v1 backup, update to v0.4 and inspect both drafts and safe preference defaults. Restore invented v0.1–v0.3 exports. Preview and cancellation must leave storage unchanged; confirmation merges once; repeated import adds no duplicates; overflow is disclosed; invalid fields/oversized files fail without partial writes. Export again and compare the seven allowed fields. Feedback backups do not include reading preferences. Native file-picker and upgrade tests are still required even when automated import tests pass.

1. Keep the intended version aligned in `package.json`, `package-lock.json`, `manifest.json`, and `data/health.json`; keep review dates tied to actual source review.
2. Run the automated commands above and `npm run build:site` from the commit intended for release. Package commands rebuild their respective output folders. Inspect source and compatibility audit results separately rather than treating a successful process exit as proof every source or site passed.
3. Inspect the ZIP: `manifest.json` must be at its root, along with the compiled scripts and UI assets, icons, bundled dictionary, and licenses. It must not contain the demo adapter, development dependencies, feedback exports, private data, or source maps.
4. Compare each archive's SHA-256 digest with its adjacent `.sha256` file. For example, from `release/` on macOS use `shasum -a 256 -c openplainenglish-0.4.0.zip.sha256`. Check the Firefox ZIP and SDK tarball separately. A checksum checks the downloaded file against the published digest; it is not a signature or a security audit.
5. Complete and record the applicable browser checks above using the extracted ZIP. The checklist itself is not evidence that a check passed.
6. Create the version tag and GitHub Release for the tested commit, attaching the versioned archives and checksums with their actual preview status. CI artifacts are for inspection; the workflow does not publish a GitHub Release, browser-store item or npm package automatically. If a manual check remains unrun, disclose it rather than marking this checklist complete.
